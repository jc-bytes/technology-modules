Code your walking stick

One program, three results

At your already-built walking stick

The sensor reads distance. Your program chooses a result. A valid near reading gives X and a sound. A valid farther reading gives a blank display and silence. An unusable reading gives ? and UNKNOWN.

Follow this guide using your working sensor program and the separate sound page.

Check: You will update one MakeCode project. The built sensor wiring stays as it is.

Help if you get stuck

Keep the model on a table during tests. This is a classroom prototype, not tested mobility equipment.

Prepare the two message variables

In MakeCode · Variables and on start

stickStatus holds the latest result. btConnected remembers whether the website is connected. Starting with UNKNOWN avoids pretending that an untested reading is far.

Create stickStatus and btConnected. In on start, set them as shown and start the Bluetooth UART service.

Check: The two variables and UART startup exist once in this program.

Help if you get stuck

Use a text block for UNKNOWN and the Logic false block for btConnected. Reuse existing matching startup blocks instead of duplicating them. This reference is not a whole sensor program. Do not paste it over your working program.

Remember connection and disconnection

In MakeCode · Bluetooth events

The website may disconnect and reconnect. These events change a flag; the sensor loop keeps choosing the display.

In Bluetooth, add on bluetooth connected and on bluetooth disconnected. Put the shown variable assignments inside them.

Check: Connecting sets btConnected true. Disconnecting sets it false and clears the old message state.

Help if you get stuck

Do not put sensor reading or a second forever loop in these events. Remove old temporary connection-display animations if they cover the sensor warning.

bluetooth.onBluetoothConnected(function () {
    btConnected = true
})
bluetooth.onBluetoothDisconnected(function () {
    btConnected = false
    stickStatus = "UNKNOWN"
})

Add the near message

In the existing valid, distance ≤30 cm branch

The same decision must drive both the display and the message. This branch is reached only after a usable reading.

Add set stickStatus to NEAR beside the existing X display.

Check: A valid near reading selects NEAR and still shows X.

Help if you get stuck

Keep the exact uppercase word. Use the existing near branch; do not add another sensor read for Bluetooth.

Add the farther message

In the existing valid, distance >30 cm branch

FAR means the latest valid measurement is farther than 30 cm. It does not prove a whole walking route is clear.

Add set stickStatus to FAR beside the existing clear screen block.

Check: A valid farther reading selects FAR and clears the display.

Help if you get stuck

Keep this branch inside the valid-reading decision. A failed reading must not fall into FAR.

stickStatus = "FAR"
// Keep the existing clear-screen block in this branch.

Add the unusable-reading message

In the existing invalid-reading branch

A missing or unusable measurement gives UNKNOWN. The older Mandrake code used 50000 as a placeholder; that must never become a large, apparently valid distance.

Add set stickStatus to UNKNOWN beside the existing ? display.

Check: The checked invalid-reading path chooses UNKNOWN, not FAR.

Help if you get stuck

Preserve the actual sensor’s failure condition. Do not copy the old 50000 rule into another sensor API without checking what it returns.

stickStatus = "UNKNOWN"
// Keep the existing question-mark display in this branch.

Send after the fresh sensor decision

In the same sensor-reading forever loop

Only one sender may remain. Remove old distance: writes and separate background transmitters; keep the sensor read. Send after the full near/far/invalid decision in this same loop. If fresh readings stop, old results must stop too.

Replace the old send with if btConnected → uart write line stickStatus, then one checked 500 ms pause.

Check: Only NEAR, FAR or UNKNOWN is sent after each fresh decision in the sensor loop.

Help if you get stuck

Do not create another forever sender. Reconcile an existing sensor pause with your teacher instead of stacking waits. The website expects NEAR/FAR/UNKNOWN, not distance: numbers.
